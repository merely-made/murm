# Independent OpenRQ qualification

This directory contains an authored MPL-2.0 process wrapper and regeneration
script. The external Java codec is OpenRQ, pinned to commit
`45f4437ba96d7e69a6ee05a2e51cf79cda90448e`. Its source and license remain
Apache-2.0; `OpenRQ-LICENSE.txt` is an exact copy of the pinned upstream license.
No OpenRQ source, Java runtime, compiled classes, or new production dependency is
imported into the repository.

The committed `../vectors/openrq-interop.json` holds independent implementation
vectors and captured decoder observations. They establish agreement for the
named objects, encoding-symbol IDs and delivery schedules. They do not establish
full RFC6330 conformance, universal recovery from any K symbols, measured recovery
probability, radio interoperability, or throughput.

## Reproduction

The portable toolchain currently qualified here is Eclipse Temurin
`jdk-21.0.8+9`, macOS aarch64. Both upstream archives have fixed SHA256 digests in
`openrq_interop.py`, checked before extraction or execution. Each run extracts
fresh source/runtime files from those archives and rebuilds the peer with
`javac --release 8 -g:none`. Main OpenRQ resources are copied without changes.
The upstream archive's unused `src/opt` symlink points into the author's home
directory; the script omits that member and records the omission.

From the suite directory, bootstrap and explicitly write a new fixture:

```sh
cargo build --locked --manifest-path Cargo.toml
python3 interop/openrq_interop.py --build-rust-peer --bootstrap \
  --write-fixture vectors/openrq-interop.json \
  --receipt results/openrq-live.json
```

The cache defaults to `~/.cache/retinue-transport-conformance/openrq`. Set
`--tools-dir PATH` to use a different external cache, or a directory actually
ignored by Git. The script rejects an unignored cache inside the checkout.
Bootstrapping explicitly retrieves the pinned archives; subsequent checks use
those archives without network access. Cargo dependency acquisition is separate.

The normal local check rebuilds current Rust source offline and verifies freshly
generated bytes against the committed fixture. It does not overwrite the corpus:

```sh
python3 interop/openrq_interop.py --build-rust-peer \
  --receipt results/openrq-live.json
```

`--rust-peer PATH` instead selects an already built process peer. The live receipt
records that executable's SHA256, the run time in UTC, upstream source/resource
digests, wrapper/generator digests, JDK archive digest, and compiled-class digest.
Missing infrastructure or a different host profile fails with an explicit
infrastructure-unavailable message. The ordinary offline Rust suite consumes the
committed corpus and requires no Java toolchain.

## Shared profile and cases

OpenRQ's pinned `InternalConstants.Al` is 1, and its OTI parser rejects other
alignments. This independent profile therefore uses exact `Al=1, N=1` OTI bytes.
The foundation suite retains its separate `Al=4` profile. The independent peer
bounds objects to 65,536 bytes, symbols to 256 bytes, source blocks to 16, source
symbols per block to 256, ESIs to 4,095 and requests/deliveries to 1,024 packets.
Every request is bounded to 512 KiB and completely validated before codec work.
Each packet carries a four-byte RFC6330 payload ID and one full T-byte symbol.

The six authored objects use `T=128`, deterministic nonzero data, and the following
source-block sizes. The first three K-prime values come from the pinned OpenRQ
systematic-indices table, which implements RFC6330 Table 2.

| F | Z | K per block | K-prime per block | Boundary exercised |
|---:|---:|---|---|---|
| 1280 | 1 | 10 | 10 | K equals first K-prime |
| 1281 | 1 | 11 | 12 | K-prime extension and partial final symbol |
| 1536 | 1 | 12 | 12 | K equals second K-prime |
| 1537 | 1 | 13 | 18 | Next K-prime extension and partial final symbol |
| 2561 | 2 | 11, 10 | 12, 10 | Unequal two-block partition and padding |
| 4097 | 2 | 17, 16 | 18, 18 | Two-block partition with K-prime extension |

For each block, the corpus includes every source symbol and the first K+8 repair
symbols, beginning at ESI=K. The campaign compares every Java-encoded byte with
the Rust encoder's bytes, decodes Java packets with Rust, and decodes actual Rust
packets with Java. Each direction exercises all source symbols, mixed loss,
repair-only delivery, and reversed repair packets with duplicates.

OpenRQ omits final-source zero padding in its transport representation. The Java
wrapper restores those zero bytes to T before comparison, without changing
payload IDs, OTI, or repair-symbol bytes. That normalization is explicit in the
fixture provenance; short source packets and multi-symbol packets are outside
this complete-symbol profile.

Each fixture scenario retains the actual Java decoded object and a SHA256 over
the concatenated full Rust frames used in that delivery order, including
duplicates. The offline Rust check replays the Java vectors and binds the
captured Java observation to its current Rust packet bytes. Its receipt labels
the Java decode as captured evidence. The optional local process campaign runs
both decoders live again.

## Binary process protocol

Integers are unsigned and big endian. Requests have magic `RQI1`, command `E` or
`D`, then the exact 12-byte RFC6330 OTI.

- `E`: u32 object length, object bytes, u16 ID count, then four-byte payload IDs.
- `D`: u16 packet count, then repeated u16 packet length and full packet bytes.

Responses have magic `RQO1` and the same command.

- `E`: u16 packet count, then repeated u16 packet length and full packet bytes.
- `D`: completion byte 0 or 1; if 1, u32 object length and decoded object bytes.

The process exits nonzero and writes a reason to stderr for an invalid request.
No codec library is shared across the Java and Rust processes. Their agreement
is implementation-interoperability evidence, subject to the coverage limits
above, rather than an independent proof of every normative requirement.
